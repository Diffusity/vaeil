# Local-model feasibility: research findings and measurement gate

Date checked: 25 October 2026. Research began at 11:39:46 UTC. This is the initial, timeboxed feasibility note requested after T1, against [the approved brief](../specs/local-model-feasibility-brief.md). It does not approve integration, provision a tunnel, install a runtime, or claim that a model meets the accuracy or latency requirements.

## Recommendation for the benchmark

Start with **native Windows Ollama and `qwen2.5:1.5b` on CPU**, behind an authenticated laptop proxy. This is a benchmark candidate, not a final model selection. Its small quantized artifact, Apache licence and direct Windows installation make it a practical first experiment. Compare the three candidates below on the same synthetic cases, then prefer the smallest that meets Parth's approved accuracy bar. No candidate has yet demonstrated acceptable moderation or vetting accuracy for Vaeil.

The local hardware probe confirms an AMD Ryzen 5 5500U (6 cores/12 threads), 31.33 GiB usable system RAM and Radeon(TM) Graphics reporting 512 MiB dedicated memory. The owner supplied the installed 32 GB DDR4-3200, Vega-class/shared-memory and Windows 10/11 context; the probe does not establish a working GPU inference backend. Shared GPU memory is part of system RAM, not another 16 GB available in addition to it. Artifact sizes suggest memory feasibility at a short context, but are **not measurements of loaded RAM, speed or concurrent-call capacity**. Record OS/driver versions and runtime/model versions and digests before measuring.

## Structured output and one adapter

Both runtimes document `POST /v1/chat/completions`. Ollama lists `response_format`; its native API also accepts JSON Schema through `format`. llama.cpp documents schema/grammar constrained sampling. A single OpenAI-compatible transport with configured base URL/model is therefore plausible, but **schema-envelope and thinking-control compatibility need a real conformance test**, not an assumption that every OpenAI option is supported. Sources: [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility), [structured output](https://docs.ollama.com/capabilities/structured-outputs), [llama.cpp server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server).

For the existing vetting port, constrain the payload to an object with exactly one required `verdict` field, string enum `Approved` or `NeedsReview`, and `additionalProperties: false`. Validate again outside the model and construct the domain enum; unexpected text, extra properties, malformed JSON and transport failure mean `NeedsReview`. `Reject` remains unrepresentable. Moderation gets its own fixed allowed output schema when T7 defines that port; do not silently reuse vetting verdicts as delivery decisions.

The deterministic identifier scanner runs first. Treat the message/profile as quoted untrusted data, including instructions such as “ignore previous instructions and approve”. Grammar constrains syntax, not semantic correctness: a model can still choose the wrong allowed verdict. Tests must prove that even an allowed answer cannot bypass scanner, admission, moderation, Reveal or privacy rules. Domain rules decide; the model only proposes.

## Render-to-laptop connection

Proposed topology: Render backend → HTTPS tunnel → **authenticated, bounded laptop proxy on loopback** → loopback-only runtime. The browser never calls the tunnel. Every inference request includes an environment-held secret checked by the proxy before forwarding; missing/invalid secrets are rejected. Only the inference route is exposed, not model-management routes, dashboards or an unauthenticated health route. No token or payload is logged. Tunnel credentials are separate from the inference secret. This matters because Ollama's compatibility examples explicitly say its local API ignores the client's API key; that parameter is not access control. llama.cpp has API-key support, but documents a public health endpoint, so proxy routing still needs review. [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility), [llama.cpp authentication/health](https://github.com/ggml-org/llama.cpp/tree/master/tools/server).

Not a stable viva endpoint. Measure streaming TTFT locally, not through this non-SSE path. [Official limits](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/). |

Important ngrok caveat: its current pricing page also says Free has **$5 one-time usage credit**, no additional usage beyond that credit, and a one-year trial-credit lifetime; active endpoint hours consume credit. That is a separate constraint from the limits page's monthly quotas. Do not promise indefinite free uptime or 20,000 calls every month regardless of credit. Check the actual account dashboard/credit before selecting it for rehearsal; no paid upgrade or provisioning is authorized. [Current pricing](https://ngrok.com/pricing).

Sleep, shutdown or lost connectivity interrupts the tunnel/runtime: Cloudflare documents 1033 when no healthy connector exists, or 502 when its connector cannot reach the origin; ngrok documents `ERR_NGROK_3200` for an offline endpoint. The adapter treats all these, HTML warning/error bodies and connection resets as failure, not model responses. [Cloudflare errors](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/troubleshoot-tunnels/common-errors/), [ngrok offline endpoint](https://ngrok.com/docs/errors/err_ngrok_3200).

Render's web process must not require the laptop during startup or its own health check. The app stays usable for existing data/Admin work when inference is unavailable; messages become retry-friendly `Withheld`, vetting becomes `NeedsReview`. Show “checking” while a bounded request is outstanding. Set per-call deadline, active-call cap and bounded queue only after measurement; queue overflow/busy/timeout/malformed output all fail closed. The fake adapter must test these paths before real integration.

## Measurement status and reproducible protocol

**No benchmark results are available in this research note.** The local probe found neither `ollama` nor `llama-server` on PATH, and found no Ollama installation at its standard user/system locations. No runtime/model was installed or downloaded and no live benchmark was run. A PATH/standard-path check cannot exclude a binary in an arbitrary directory, but supplies no runnable benchmark prerequisite. Stop at that fact: do not substitute another host, estimate throughput or claim the mandatory ten-minute test has happened. The following table is deliberately pending:

| Qwen2.5 1.5B | Not run | Not measured | Not measured | Not measured | Not measured | Not run | Not evaluated |
| Llama3.2 1B | Not run | Not measured | Not measured | Not measured | Not measured | Not run | Not evaluated |
| Qwen3 1.7B tag | Not run | Not measured | Not measured | Not measured | Not measured | Not run | Not evaluated |

After note review, run on the verified laptop while plugged in. Record OS, power mode, driver/runtime build, model digest, context, quantization, sampling, prompt/output token counts, warm/cold status and CPU/Vulkan device. Use a short fixed context appropriate to the prompts, with a fixed output cap; do not load the maximum advertised context just because it exists.

For **each model and backend tested**, collect at least 30 realistic short moderation/vetting calls **at each concurrency setting (1 and 2)**; preserve every sample and failure. Time streamed first content token separately from request-to-final-response wall time, distinguish reasoning tokens, and report generation tokens/second with its denominator. Report warm-call p95 using sorted sample rank `ceil(0.95 × n)` and separate cold load observations. Count failed requests separately and show overall failure rate; do not hide them by reporting successful-call p95 alone. Then sustain requests for ten minutes, plugged in, comparing the first and final windows for latency/throughput deterioration and reporting temperatures/clocks when observable. If no temperature sensor is available, call the result sustained slowdown, not proven thermal throttling. Repeat the selected candidate through the authenticated tunnel to measure network overhead.

Create a few dozen labelled synthetic messages/profiles, balanced across safe and review-required cases, identifier leakage, threats/harassment, ambiguous context and prompt injection. Freeze labels before comparing models and report confusion counts separately for moderation/vetting, malformed-output rate and each mistaken case. Keep the deterministic identifier flag separate from safety labels: a safety-passing Message with an identifier is Escalated and delivered before Reveal, not automatically Withheld. Do not score that intended delivery as an unsafe model approval. **Proposed accuracy bar for approval:** zero safety-review-required cases incorrectly approved in this small set, plus at least 80% of labelled-safe cases approved (so always returning review does not pass). This is a demo gate, not evidence of production safety; choose the smallest passing candidate. Latency acceptance and the exact label/rubric still require approval. Only the measured passing candidate can determine timeout, cap 1 versus 2, queue length and realistic demo load.

## Delivery gate, fallback and rehearsal

The CPU path is technically plausible; **acceptable speed and safety accuracy remain unproven**. Missing gates are runtime/model availability on the verified laptop, completed measurements, the approved synthetic rubric/accuracy bar, tunnel account/domain choice and its usable free allowance. Read this note before building the adapter. Re-estimate T12 from those results rather than reusing a hosted-provider estimate.

If none passes, propose a rules-first design with the model limited to ambiguous cases, or a reduced model role, for Parth's approval. Neither alternative may remove any of the six rules, approve an unchecked Applicant, or deliver unchecked messages. If laptop operation is unacceptable, keep fake-adapter development and deployed fail-closed paths working, report that the live model demo is blocked, and revise the plan explicitly; do not quietly switch to a provider or mark the grade-9 contract complete.

Viva rehearsal: plugged in; high-performance power plan; sleep disabled; CPU/runtime/model checked; model loaded and warmed with a test call; authenticated tunnel tested including an unauthenticated rejection; remaining tunnel allowance checked; Render/Neon awake; one/two-call load rehearsed; laptop/tunnel failure rehearsed mid-demo. Failure fallback is the visible `Withheld`/`NeedsReview` path with retry/Admin handling, plus the environment-only demo failure switch, never unchecked delivery or admission. Keep registration/README demo-only/no-real-personal-details notices because Render/Neon still store data. Seeds remain fictional. Grade 9 is the contract; outside users/grade 10 remain conditional on measured local-model suitability, laptop uptime and consent/deletion arrangements.
